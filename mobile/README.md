# delivery_app (mobile)

Flutter client for the delivery marketplace app. One codebase serves all four roles —
customer, driver, vendor, admin — routed by the signed-in user's `role` field. See the
[repo root README](../README.md) for the overall project structure and Firebase setup, and
[`CLAUDE.md`](../CLAUDE.md) for architecture notes.

## Prerequisites

- Flutter SDK matching `environment.sdk: ^3.9.2` in `pubspec.yaml`
- Firebase project wiring is already checked in (`lib/firebase_options.dart`,
  `android/app/google-services.json`) — see the root README's Setup section if you need to
  repoint this at a different Firebase project
- A Maps API key for `google_maps_flutter` (live delivery tracking) — see below

## Setup

```
flutter pub get
```

## Run

```
flutter run
```

For local development against the Firebase emulator suite instead of the live project, start
the emulators from the repo root first:

```
firebase emulators:start
```

then run the app as usual — the emulator ports are Auth `:9099`, Firestore `:8080`,
Functions `:5001`, Storage `:9199`.

## Test & lint

```
flutter analyze                 # run after any lib/ change

```

## Maps API key

The Google Maps SDK key is **never committed**. Supply it locally; without one the app still
builds and runs, but `GoogleMap` widgets (live tracking, location picker) show blank grey tiles.
Use a separate key per platform, created in the Google Cloud Console for the
`delivery-app-syria-2026` project (or any project with the Maps SDKs enabled).

**Android** — add to `android/local.properties` (already gitignored):

```
MAPS_API_KEY=<your Android Maps SDK key>
```

`android/app/build.gradle.kts` reads it into a manifest placeholder, which `AndroidManifest.xml`
uses as `${MAPS_API_KEY}`. Rebuild after changing it. Restrict the key in the Cloud Console to
*Android apps* (package `com.deliveryapp.delivery_app` plus the SHA-1 of each signing certificate —
debug and release) and, under *API restrictions*, to **Maps SDK for Android** only.

**iOS** — create `ios/Flutter/Maps.xcconfig` (already gitignored):

```
MAPS_API_KEY = <your iOS Maps SDK key>
```

`Debug.xcconfig`/`Release.xcconfig` optionally include it, `Info.plist` exposes it as `GMSApiKey`,
and `AppDelegate.swift` passes it to `GMSServices.provideAPIKey`. Restrict the key to *iOS apps*
(your bundle identifier) and to **Maps SDK for iOS** only.

**Mapbox (separate)** — place search and reverse geocoding use a Mapbox *public* token, not the
Google key:

```
flutter run --dart-define=MAPBOX_PUBLIC_TOKEN=pk.xxx
```

Without it, search and address suggestions are unavailable, but a map pin can still be confirmed.

**Navigation** — the driver's "Navigate to pickup / drop-off" opens a Google Maps HTTPS
directions link in the Maps app or browser; it needs no key.

Location permission is foreground-only (Android `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`,
iOS `NSLocationWhenInUseUsageDescription`); there is no background location.

## Push notifications

Order pushes are sent by the Cloud Functions order triggers through `notifyUser`
(`functions/src/notifications.ts`), in Arabic or English per the user's app language. The app
registers the device's FCM token and language on `users/{uid}` after sign-in, and a tapped
notification opens the related order (customer tracking / vendor order detail; drivers land on
their active delivery).

**Android** — works with the checked-in configuration: `firebase_messaging` adds the
`POST_NOTIFICATIONS` permission (the runtime prompt on Android 13+ is requested at sign-in), and
pushes arrive on the "Order updates" channel created in `MainActivity.kt` (set as FCM's default
channel in `AndroidManifest.xml`).

**iOS — manual setup still required** (not done in this repo; it needs a Mac with Xcode and an
Apple Developer account):

1. In the Apple Developer portal, create an APNs Authentication Key (.p8) and note its Key ID and
   your Team ID.
2. In the Firebase console (`delivery-app-syria-2026` → Project settings → Cloud Messaging → Apple
   app configuration), upload that APNs key.
3. In Xcode, open `ios/Runner.xcworkspace`, select the Runner target → *Signing & Capabilities* and
   add **Push Notifications** (this creates `Runner.entitlements` with `aps-environment`) and
   **Background Modes → Remote notifications**.
4. Build on a real device (the iOS Simulator can't receive remote pushes on older Xcode versions)
   and allow notifications when prompted.

Until these steps are done, iOS devices won't receive pushes; nothing else in the app depends on
them.

## iOS

`ios/Runner/GoogleService-Info.plist` was not generated by FlutterFire CLI (it can only embed
that file into the Xcode project from macOS). On a Mac, run
`flutterfire configure -p delivery-app-syria-2026 -y --platforms=android,ios,web` from this directory
to fill it in before building for iOS.

## Localization

Arabic-first, RTL-aware. Source strings live in `lib/l10n/app_en.arb` and `lib/l10n/app_ar.arb`;
`flutter pub get` regenerates `AppLocalizations` from them (`generate: true` in `pubspec.yaml`,
config in `l10n.yaml`). `l10n_untranslated.txt` lists any English strings missing an Arabic
translation — it should read `{}` when both files are in sync.

## Structure

```
lib/
  features/     # admin, auth, customer, driver, notifications, vendor — screens + providers
  models/       # AppUser, Order, MenuItem, etc.
  routing/      # go_router config, role-based redirect
  services/     # AuthService, FirestoreService, LocationService, PushNotificationService
  core/         # errors, parsing, theme, constants, and other cross-feature utilities
  shared/       # widgets reused across more than one feature
  l10n/         # generated + source .arb localization files
```
